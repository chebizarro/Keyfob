# Oracle Plan

# 1. **Summary**

Keyfob should evolve through a **phased productization plan, not a rewrite**: keep the existing protocol and signing primitives (`KeyfobCrypto`, `KeyfobCore`, `KeyfobPolicy`, `KeyfobBridge`, `KeyfobRelay`) intact where they already work, and add the missing product layers around them—**identity management, onboarding, permissions, history, modern crypto coverage, and a new integration layer above `KeyfobRelay` for end-to-end NIP-46**. The highest-value path is: first make Keyfob usable as a real signer for one person on Apple platforms, then make it trustworthy and low-friction, then complete the missing NIPs and remote-signer flows, and finally polish ecosystem integration and reliability.

---

# 2. **Current-state analysis**

## Relevant architecture today

### Module responsibilities

- **`KeyfobCrypto`**
  - Owns key generation, load, import/export, keychain storage, biometrics (`LAContext`), and NIP-01 signing.
  - Current limitation: **single-key mental model**; export is **AES-GCM**, not NIP-49.

- **`KeyfobCore`**
  - Owns `NostrEvent`, canonical JSON, event id computation, and `SignOrchestrator`.
  - Current flow is already good: **validate → consent → sign → audit/duration**.
  - Current limitation: orchestrator is effectively built around **signing only**, not broader signer operations.

- **`KeyfobPolicy`**
  - Owns allowlist/session/rate-limit policy and JSONL audit log persistence.
  - Current limitation: policy granularity is too coarse for a full product; it needs **per-client, per-operation, per-kind** rules and a user-manageable registry.

- **`KeyfobBridge`**
  - Owns external entry points: URL scheme, Universal Link, App Intent, XPC.
  - Current limitation: no **nostrsigner-style routing**, no **bunker/nostrconnect pairing**, and existing IPC is not yet fully multi-key/policy aware.

- **`KeyfobUI`**
  - Owns `ConsentView`.
  - Current limitation: no onboarding, history, permissions, relay management, pairing, or profile surfaces.

- **`KeyfobWebShared`**
  - Owns `window.nostr` bridge definitions/content.js for NIP-07.
  - Current limitation: capability surface stops at what the app currently supports.

- **`KeyfobRelay`**
  - Already substantial and reusable:
    - `RelayConnection`
    - `RelayPool`
    - `SubscriptionManager`
    - `NIP46Handler`
    - `EventDeduplicator`
    - `PublishInspector`
    - `RelayInfo`
    - `RelayTelemetry`
  - Critical constraint: **intentionally zero-dependency**.
  - Current limitation: NIP-46 transport exists, but cannot reach actual keys or signer policy on its own.

## Existing end-to-end flow

### Browser/App signing path today

`Safari extension / Action extension / App Intent / XPC / URL router`
→ `KeyfobBridge`
→ `KeyfobCore.SignOrchestrator`
→ `KeyfobPolicy.PolicyEngine`
→ `KeyfobUI.ConsentView` if needed
→ `KeyfobCrypto.KeyManager`
→ result + audit log

This path should be **reused**, not replaced.

### Relay/NIP-46 path today

`RelayConnection / RelayPool`
→ `NIP46Handler` subscribes and receives kind `24133`
→ decrypt/route/respond scaffolding exists
→ **stops short of real signing**, because `KeyfobRelay` cannot depend on crypto/core/policy

This is the key architectural gap.

## Reusable assets that should be extended, not duplicated

- `CanonicalJSON` and `NostrEvent`
- `SignOrchestrator`
- `PolicyEngine`
- JSONL audit persistence
- `ConsentView`
- `RelayTelemetry`
- `NIP46Handler`
- Existing IPC surfaces in `KeyfobBridge`
- Existing Safari/web-extension NIP-07 plumbing

## Hard constraints

- **OS floor:** iOS 15+, macOS 12+
  - This means **no SwiftData**; persistence must be app-group/file/Keychain based.
- **Security boundary:** keys must remain in **Keychain / helper process / secure boundary**.
- **Apple-native UX:** SwiftUI and extension-safe APIs.
- **Modularity:** `KeyfobRelay` must remain zero-dependency.
- **Cross-target sharing:** app, extensions, and helper need shared policy/identity metadata via **app group + keychain access group**.
- **App Store compliance:** pairing, URL handling, camera access, and background behavior must stay within platform rules.

## What is blocking product readiness

1. No onboarding or identity lifecycle UI.
2. No multi-key support.
3. No persistent, user-visible permission model.
4. No history/forensics UX.
5. Missing NIP-44, NIP-04, NIP-06, NIP-19, NIP-49.
6. No end-to-end NIP-46 integration.
7. No pairing UX (`bunker://`, `nostrconnect://`, QR).
8. No relay management or profile display.
9. No signer-specific external protocol like `nostrsigner://`.

## Change strategy: targeted expansion, not broad refactor

This should be treated as a **broader product expansion with targeted architectural additions**, not a rewrite:
- **Do not refactor `KeyfobRelay` into a crypto-aware module.**
- **Do add one integration module above it** for remote signing.
- **Do evolve `KeyfobCrypto`, `KeyfobCore`, and `KeyfobPolicy`** to support multi-key and generalized signer operations.
- **Do keep the existing signing flow as the canonical path** for all future operations.

# 3. **Design**

## Cross-cutting design decisions

### A. Introduce a generalized signer operation model
Instead of building separate logic for sign, encrypt, decrypt, get-public-key, and remote-sign methods, extend the current orchestrator model to a closed operation set such as:

```text
SignerOperation
- getPublicKey
- signEvent(event)
- nip04Encrypt(peerPubkey, plaintext)
- nip04Decrypt(peerPubkey, ciphertext)
- nip44Encrypt(peerPubkey, plaintext)
- nip44Decrypt(peerPubkey, payload)
- exportPrivateKey(format)
- pairRemoteSigner(connectionRequest)
```

**Why:** one policy engine, one audit trail, one consent system, one history model.

### B. Split secret storage from identity metadata
Secrets stay in Keychain; multi-key product state needs separate metadata:

```text
IdentityMetadata
- id: UUID
- keyAlias: String
- publicKeyHex: String
- displayName: String?
- source: generated | importedHex | importedNsec | importedMnemonic
- createdAt: Date
- lastUsedAt: Date?
- isActive: Bool
```

**Why:** multi-key UI, migration, history, and permissions all need stable identity IDs without duplicating secret material.

### C. Use shared file/app-group persistence, not SwiftData
Persist:
- identity metadata
- policy rules
- client registry
- relay configuration
- history index / audit views

using an **app-group-backed store** with atomic writes and serialized access.

**Why:** OS baseline excludes SwiftData.

### D. Add a new integration target above `KeyfobRelay`
Proposed module: **`KeyfobSignerIntegration`** (name can vary, role should not)

Depends on:
- `KeyfobRelay`
- `KeyfobCrypto`
- `KeyfobCore`
- `KeyfobPolicy`

Owns:
- NIP-46 method dispatch
- decrypt/encrypt bridging
- pairing/session state
- relay-backed signer lifecycle

**Why:** preserves `KeyfobRelay` zero-dependency guarantee.

## Phase 1 — **Identity foundation and first-run productization**  
**Priority:** P0  
**Rationale:** Keyfob is not yet a product a user can install and succeed with on first launch. This phase creates a usable signer.

### Tasks

| Task | Scope | Modules | Dependencies | Effort |
|---|---|---|---|---|
| 1. Multi-key identity model | Add identity metadata store, active identity selection, migration from singleton key state | `KeyfobCrypto`, app targets | None | L |
| 2. Multi-key crypto API evolution | Make signing/load/export/import APIs identity-addressable instead of implicit singleton | `KeyfobCrypto`, `KeyfobCore`, `KeyfobBridge` | Task 1 | L |
| 3. NIP-19 core support | Add `npub`/`nsec` display and input parsing; optionally full entity support if low incremental cost | `KeyfobCrypto` or `KeyfobCore`, `KeyfobUI` | Task 2 | M |
| 4. Onboarding flow | Create/import key flow, first-run active key selection, biometric explanation, backup reminder | `KeyfobUI`, iOS app, macOS app | Tasks 1–3 | M |
| 5. Key management UI | Identity list, rename, set active, show `npub`, copy/share public identity | `KeyfobUI`, app targets | Tasks 1–3 | M |
| 6. Entry-point gating | If no active identity exists, IPC routes show onboarding instead of failing obscurely | `KeyfobBridge`, iOS/macOS apps, extensions | Tasks 1, 4 | M |

### State and data flow introduced

- **First run**
  - Trigger: app launch with no identity metadata
  - Flow: app target → onboarding view → create/import action → `KeyfobCrypto` writes secret to Keychain → metadata store writes `IdentityMetadata` → active identity set → UI dismisses → existing signing entry points now resolve active key
  - Observation: published shared app state / view model refresh
  - Out-of-order handling: if an extension fires before onboarding completes, it should fail with a user-visible “No active identity configured” state, not a low-level crypto error

- **Migration from existing installs**
  - Trigger: first launch after upgrade
  - Flow: existing singleton key detected → synthesize one `IdentityMetadata` record → mark active → leave secret untouched
  - Duplicate protection: migration must be idempotent; use a persisted schema version marker

### API/interface changes

- `KeyfobCrypto` moves from implicit singleton operations to identity-scoped operations.
- All callers in:
  - `KeyfobCore.SignOrchestrator`
  - `KeyfobBridge` XPC/AppIntent/URL handling
  - app/extension consent flows  
  must pass a resolved identity ID or active-identity lookup result.

### Priority justification

This phase is first because **every later feature assumes a real user can create/import/select a key**. Without it, NIP-46, permissions, and history all land on top of a product that still cannot onboard users cleanly.

## Phase 2 — **Trust model, permissions, and low-friction approval**  
**Priority:** P0  
**Rationale:** Once onboarding exists, the next differentiator is a signer that feels safe and low-friction, not a raw protocol demo.

### Tasks

| Task | Scope | Modules | Dependencies | Effort |
|---|---|---|---|---|
| 1. Generalize orchestration to `SignerOperation` | Extend `SignOrchestrator` to handle all signer actions through one pipeline | `KeyfobCore` | Phase 1 | L |
| 2. Per-client registry | Persist client identity across web origins, bundle IDs, XPC callers, and future remote signer peers | `KeyfobPolicy`, `KeyfobBridge` | Task 1 | M |
| 3. Per-client/per-kind permissions | Add rules by identity + client + operation + optional event kind + expiry/session mode | `KeyfobPolicy`, `KeyfobCore` | Tasks 1–2 | L |
| 4. Signing policy presets | Implement “Basic auto-approve” and “Manual per-app” as top-level product modes | `KeyfobPolicy`, `KeyfobUI` | Task 3 | M |
| 5. History view | Turn audit log into user-facing history with filters and detail screens | `KeyfobPolicy`, `KeyfobUI`, app targets | Tasks 1–3 | M |
| 6. Consent UX v2 | Show client identity, event kind, active identity, session/rate-limit state, and permission shortcut actions | `KeyfobUI`, `KeyfobCore` | Tasks 1–4 | M |

### Policy model to add

```text
ClientRecord
- id: String
- clientType: webOrigin | xpcBundleId | appIntentSource | remotePubkey
- displayName: String?
- platform: iOSApp | macOSApp | SafariWeb | RemoteSigner
- firstSeenAt: Date
- lastSeenAt: Date
- trustState: unknown | approved | blocked

PermissionRule
- id: UUID
- identityId: UUID
- clientId: String
- operation: getPublicKey | signEvent | nip04Encrypt | nip04Decrypt | nip44Encrypt | nip44Decrypt
- eventKind: Int?   // nil = all kinds
- decision: allow | prompt | deny
- sessionDurationSeconds: Int?
- expiresAt: Date?
- createdAt: Date
- updatedAt: Date
```

### Recommended default behavior

- **Basic auto-approve (recommended)**
  - `getPublicKey`: allow after first client trust approval
  - `signEvent`: first request per client prompts; accepted requests create a timed session (for example 10–15 minutes) for that identity/client; rate limits still apply
  - crypto/decrypt operations: prompt on first use, then follow session policy
  - export/reveal/backup operations: always prompt + biometric

- **Manual per-app**
  - every signing/encryption/decryption request prompts unless the user explicitly creates a persistent allow rule

### Error handling / edge cases

- Unknown client → prompt, do not fail closed silently
- Rate-limit exceeded → deny with clear reason in UI/history
- Missing active identity → redirect to onboarding
- Client deleted but history retained → show tombstoned client label rather than dropping history rows

### Priority justification

This is the earliest point where Keyfob becomes meaningfully better than “a signer that asks too many questions” or “a signer that trusts too much.” It is core to **minimal friction without sacrificing trust**.

## Phase 3 — **Protocol completeness and recovery safety**  
**Priority:** P1  
**Rationale:** This phase fills the protocol gaps that real Nostr ecosystems expect and removes backup/export weaknesses.

### Tasks

| Task | Scope | Modules | Dependencies | Effort |
|---|---|---|---|---|
| 1. NIP-06 mnemonic import/derivation | BIP39 mnemonic parsing + seed derivation + account/path conventions + import UI | `KeyfobCrypto`, `KeyfobUI` | Phase 1 | L |
| 2. NIP-49 `ncryptsec` export/import | Add scrypt + XChaCha20-Poly1305 private key encryption; default all new exports to NIP-49 | `KeyfobCrypto`, `KeyfobUI` | Phase 1 | L |
| 3. Legacy export compatibility | Keep current AES-GCM import path for older backups; make legacy export non-default | `KeyfobCrypto`, `KeyfobUI` | Task 2 | M |
| 4. NIP-44 encrypt/decrypt | Implement modern payload encryption required for NIP-46 and future client ops | `KeyfobCrypto`, `KeyfobCore` | Phase 2 Task 1 | L |
| 5. NIP-04 encrypt/decrypt | Implement deprecated compatibility path for apps still using it | `KeyfobCrypto`, `KeyfobCore` | Phase 2 Task 1 | M |
| 6. Policy/audit integration for crypto ops | Route NIP-04/NIP-44 through permissions/history/session logic | `KeyfobCore`, `KeyfobPolicy`, `KeyfobUI` | Tasks 4–5 | M |

### Data and mutation points

- **Mnemonic import**
  - Trigger: onboarding/import screen
  - Flow: UI input → mnemonic validator → seed derivation → private key derivation → Keychain write → identity metadata write
  - Failure modes: invalid checksum, unsupported derivation path, duplicate imported pubkey

- **NIP-49 export**
  - Trigger: user backup/export action
  - Flow: biometric gate → key fetch in secure boundary → `ncryptsec` generation → share/save sheet
  - Failure modes: scrypt timeout/resource issues, canceled biometric, I/O failure to export destination

### Persistence and migration

- New export default: **NIP-49 only**
- Existing AES-GCM backups:
  - new app version should still import them
  - old app versions will not understand `ncryptsec`; document this as non-rollback-safe for newly created backups

### Priority justification

These features are not first because a signer must first be usable and safe. They become next because **backup/recovery and modern crypto support are table stakes** once real users trust the app with keys.

## Phase 4 — **Full NIP-46 remote signer product**  
**Priority:** P1  
**Rationale:** `KeyfobRelay` already contains the transport machinery; wiring it into real crypto and policy turns Keyfob into a true remote signer, which is one of the biggest value unlocks left.

### Tasks

| Task | Scope | Modules | Dependencies | Effort |
|---|---|---|---|---|
| 1. Add relay integration module | Create `KeyfobSignerIntegration` above `KeyfobRelay` to bridge NIP-46 requests to crypto/core/policy | new module + `KeyfobRelay` consumers | Phases 2–3 | L |
| 2. NIP-46 method router | Support `ping`, `connect`, `get_public_key`, `sign_event`, and crypto methods using unified operation flow | `KeyfobSignerIntegration`, `KeyfobCore` | Task 1 | M |
| 3. Pairing URL support | Parse and route `bunker://` and `nostrconnect://` URLs | `KeyfobBridge`, app targets, integration module | Task 1 | M |
| 4. QR pairing UX | iOS camera scanner; macOS paste/import-image/Continuity fallback | app targets, `KeyfobUI` | Task 3 | M |
| 5. Relay configuration UI | Global relays, per-pairing relays, validation, connect state, remove/reorder | `KeyfobUI`, app targets, integration module | Task 1 | M |
| 6. Remote connection management | Show paired apps, relay URLs, last seen, auth state, permissions, disconnect/revoke | `KeyfobUI`, `KeyfobPolicy`, integration module | Tasks 2–5 | M |
| 7. End-to-end audit/history | Remote signer requests appear in the same history and permission system as local ones | `KeyfobPolicy`, `KeyfobCore`, integration module | Tasks 1–2 | S |

### New component

**`KeyfobSignerIntegration`**  
Kind: SPM module/service layer

Owns:
- one or more relay-backed signer sessions
- mapping from NIP-46 RPC request → `SignerOperation`
- encrypt/decrypt of request/response payloads using NIP-44 (and NIP-04 where needed)
- pairing state and lifecycle
- handing responses back to `NIP46Handler`

Does **not** own:
- websocket transport internals
- secret key storage
- UI state persistence

### NIP-46 flow after integration

`bunker://` / `nostrconnect://` / QR
→ `KeyfobBridge`
→ pairing record persisted
→ `KeyfobSignerIntegration` starts relay session via `RelayPool`
→ `NIP46Handler` receives encrypted request
→ integration module decrypts via `KeyfobCrypto`
→ maps to `SignerOperation`
→ `KeyfobCore.SignOrchestrator`
→ `KeyfobPolicy.PolicyEngine`
→ consent UI if needed
→ `KeyfobCrypto` executes
→ integration module encrypts response
→ `KeyfobRelay` publishes response

### Concurrency/lifecycle

- Relay callbacks likely occur off-main-thread; integration module should own an **actor/serialized queue** for pairing/session state.
- UI prompts must hop to main actor.
- Cancellation:
  - if relay disconnects mid-request: request marked failed in history, no partial approval state retained
  - if user dismisses approval: send NIP-46 error response, do not retry automatically

### Priority justification

This lands after protocol and trust foundations because remote signing is only valuable once the app can safely manage identities, permissions, and crypto methods end-to-end.

# 5. **Risks and migration**

## 1. Single-key → multi-key migration
- **Risk:** existing installs may have one secret with no metadata.
- **Plan:** on first launch after upgrade, create exactly one `IdentityMetadata` record from the existing key and mark it active.
- **Rollback note:** safe if metadata store is additive and secret storage remains unchanged.

## 2. Export format migration to NIP-49
- **Risk:** newly created `ncryptsec` backups will not be importable by older Keyfob versions.
- **Plan:** keep legacy AES-GCM import indefinitely; make legacy export an explicit “compatibility export” option if retained at all.
- **User-facing note:** clearly label the new default export format.

## 3. Cross-process persistence races
- **Risk:** app, extension, and helper may mutate policy/history/identity metadata concurrently.
- **Plan:** use serialized writes, atomic file replacement, and file locking or a single-writer service where practical.
- **Validation:** stress-test simultaneous sign requests from Safari + XPC helper.

## 4. Unknown extension points in `NIP46Handler`
- **Risk:** current public API may not expose enough hooks for the integration layer without small relay changes.
- **Plan:** validate whether `NIP46Handler` can already hand out raw request envelopes and publish responses; if not, add the smallest possible transport-only hooks.
- **Validation:** trace one full fake NIP-46 request through tests before coding UI.

## 5. Entitlement and access-group assumptions
- **Risk:** app, extensions, and helper may not all share the same keychain/app-group setup today.
- **Plan:** audit entitlements before implementation.
- **Validation:** test key read/write and metadata read/write from every target on-device.

# 6. **Implementation order**

1. **Audit shared storage and entitlement assumptions**
   - Validate keychain access groups, app group storage, and current singleton key migration path.
   - Must happen first.

2. **Add identity metadata store and active-identity model**
   - Keep secret storage unchanged initially.
   - Independently testable.

3. **Evolve `KeyfobCrypto` APIs to be identity-addressable**
   - Update core callers but keep old behavior shimmed until all call sites move.
   - Atomic with call-site updates.

4. **Ship onboarding + key management + no-identity entry-point handling**
   - First user-visible milestone.

5. **Generalize `SignOrchestrator` into a unified signer operation pipeline**
   - Required before permissions, NIP-04/44, and NIP-46.

6. **Expand `PolicyEngine` into per-client/per-operation/per-kind permissions + history UI**
   - This makes current local signing surfaces production-worthy.

7. **Implement NIP-19, NIP-06, NIP-49, NIP-44, and NIP-04**
   - Land crypto primitives before wiring remote signing.
   - NIP-44 should precede NIP-46 integration.

8. **Add `KeyfobSignerIntegration` and wire end-to-end NIP-46**
